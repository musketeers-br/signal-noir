Feature: prior receipt (P9).

Describe the behavior:
1. During Investigation or Reconciliation, the system may find a candidate receipt for the same real order under another transaction identifier and another orderId.
2. The system obtains the candidate receipt and the raw Order snapshot through read-only tools. The Simulator never returns a ready-made equivalence key.
3. The core canonically computes the equivalence key for both Orders. If the keys match, the Validator confirms the closure. The Case moves to ResolvedByPriorReceipt, links the earlier receipt, and no Execution occurs.
4. If the keys do not match, or the identity is ambiguous, the Case moves to ReviewRequired with the candidate and its divergent fields in the Dossier. There is no automatic closure by inference.
5. The closure records the prior receipt reference, the equivalence key evidence and the fact that nothing was resent.
6. No new Action enters the catalog for this behavior. The representation is whatever the contract-change defines: a no-effect closure or an existing mechanism without a new effect Action.

Acceptance scenarios:
- Confirmed equivalence: ResolvedByPriorReceipt, no Execution, prior receipt linked.
- Mismatched equivalence: ReviewRequired with the candidate in the Dossier.
- Ambiguous identity: ReviewRequired, no automatic closure.
- No tool returns a ready-made equivalence key.
- The prior receipt can be found by receipt search and by the origin order snapshot.
- No effect is sent and no duplicate receipt is created.

Out of scope: general Execution behavior, the console, the Benchmark, a new Action outside the catalog.

Success criteria: a prior receipt closes the Case only after deterministic equivalence confirmation; every uncertain case goes to review with the candidate; no resend happens.

Anchors: contracts/openapi-sim.yaml (receipts, origin orders); contracts/openapi-signalnoir.yaml (prior-receipt fields).
