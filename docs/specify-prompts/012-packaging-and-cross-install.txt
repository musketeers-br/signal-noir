Feature: packaging, installation and cross-install validation.

Describe the behavior:
1. From a clean installation, `docker compose up` starts the application using the locally loaded AI Hub build 154 image. The build 162 is not accepted. No AI Hub image, nor any image derived from it, is pushed to a public registry.
2. The README is in English and covers: the `docker load` of the build 154 files (x64 and ARM64), the retag to the exact tag used by compose, the image and build used, the supported providers and the key environment variable, the start/validate/benchmark commands, how the product works, the video link, the team's DC profiles, the limitations (synthetic data and Replay) and the reset behavior.
3. Secrets enter only at runtime through `.env` or environment variables. No key is committed, baked into the image, written to a Case, Timeline, log or export. Without a valid key, the application starts, reports the provider as unavailable, and Cases that need the provider end in ReviewRequired with that reason.
4. Durability: data survives `docker compose restart` and `stop`/`start`. `docker compose down` recreates the demo state, and the README says so.
5. Cross-install: a team member who did not write the README installs on a clean machine and runs the smoke test with their own key, reaching the first Case in at most 15 minutes.
6. The quick validation command runs 3 reference cases in at most 3 minutes and reports match/diverged with a reason.
7. CI performs static analysis and, if viable on a public IRIS image, the core unit tests. No workflow publishes, pushes or deploys an image.
8. The demonstration video is at most 5 minutes, follows the demo script, covers the decision, platform-guarantee, dossier and resilience moments, and labels synthetic data and Replay.
9. Submission: the Open Exchange page points to the public repository and the contest entry is verified. Only tested platforms and providers are announced as validated. Published results match the benchmark report. Profiles and links are verified.

Acceptance scenarios:
- Clean install following only the README: the application starts and the smoke reaches the first Case.
- Start without a key: the app is up, the provider is unavailable, and the affected Cases are in ReviewRequired.
- Restart and stop/start: Case, Approval and Timeline survive.
- Down and up: the documented reset behavior matches the README.
- Search the image, repository, logs and exports for the key: nothing is found.
- Quick validation: 3 cases, ≤ 3 minutes, per-case match/diverged.
- CI: no image publication.
- Cross-install by a different team member: succeeds with their own key.
- Video: ≤ 5 minutes, labels synthetic and Replay, matches the delivered version.

Out of scope: new product behavior, new endpoints, new Actions, changes to the benchmark result.

Success criteria: a new team member installs and runs the smoke using only the README; no secret leaks; restart and reset behave as documented; no untested platform is announced as validated.

Anchors: contracts/openapi-signalnoir.yaml (quick validation endpoints if any); benchmark report.
