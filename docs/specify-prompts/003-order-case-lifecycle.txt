Feature: Order intake and Case lifecycle.

Describe the behavior:
1. Receive a synthetic JSON Order through a defined entry point. Validate its structure before any delivery attempt. An invalid Order is rejected with a recorded reason and produces no Attempt.
2. Correlate the Order with its business orderId, transaction identifier and correlation IDs. Keep an immutable Order snapshot and a deterministic equivalence key computed only in the core.
3. Open a Case on the first Exception. At most one non-terminal Case exists per orderId. A new Exception on a non-terminal Case is appended to that Case; a new episode after a terminal state creates a related Case.
4. Maintain a single state machine over: Open, Investigating, DecisionProposed, PendingApproval, Approved, Rejected, Executing, Held, ReviewRequired, Resolved, ResolvedByPriorReceipt, Cancelled, Failed. Each transition has an origin, a destination, an authorized actor, preconditions, an event and the subsequent work. Terminal states never reopen implicitly. Held leaves only through a new Investigation.
5. Evidence, Diagnosis, Proposal, Approval, Execution and Receipt are separate, linked records. The Timeline is append-only. A transition commits its new state, its Timeline event and its pending-work record together, in a short transaction that performs no external I/O.
6. Concurrency is optimistic. A command whose expected caseVersion, state or target no longer holds loses visibly and writes nothing.
7. Expose read projections: case list with a cursor, case detail with caseVersion, executionOutcome, currentProposal, pendingApproval, labels and lastEventSeq, and an incremental timeline by sinceSeq. Every response carries caseVersion, lastEventSeq and serverTime. All projections label synthetic data.
8. Rejection and expiry have a defined destination and limit. The first rejection may produce a new Investigation; a second rejection ends in ReviewRequired. Expiry returns the Case to a state that requires a new Proposal and, where applicable, a new Approval.

Acceptance scenarios:
- Invalid Order: rejected with a reason, no Attempt, no Case.
- Valid Order with a failed delivery: a Case is opened and the Timeline contains the failure event.
- Second Exception on the same open Case: appended, no second Case.
- New Exception after a terminal Case: a related Case is created.
- Restart: Case and Timeline survive unchanged.
- Stale expected caseVersion: no write, and the command is refused.
- Incremental timeline: no confirmed event is lost, including one confirmed late.
- List/detail/timeline: every response conforms to contracts/openapi-signalnoir.yaml and labels synthetic data.

Out of scope: Agent investigation, Validator rules, Approval decisions, Execution, the operator console, the Simulator implementation.

Success criteria: a synthetic Order becomes a durable Case with a complete, append-only Timeline; invalid input never reaches the partner; two writers can never both win the same transition.

Anchors: contracts/openapi-signalnoir.yaml; states and transitions above.
