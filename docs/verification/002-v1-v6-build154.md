## V1 — SHA-256

- `SHAHash(256, "abc")` returns 32 bytes, identical across calls, and equals the standard vector
  `ba7816bf8f01cfea414140de5dae2223b00361a396177a9cb410ff61f20015ad` (checked against Python
  `hashlib`).
- **Catch**: building D3's "first 8 bytes as an unsigned integer" with `n = n * 256 + $Ascii(h, i)`
  loses the last digits. ObjectScript keeps about 19 significant digits, and 64-bit values reach 20.

  | Input | ObjectScript, 8 bytes | Exact |
  |---|---|---|
  | `abc` | 13436514500253700070 | 13436514500253700074 |
  | `signal-noir\|P5\|order\|7` | 13060928790452382120 | 13060928790452382122 |

  The result is still deterministic inside IRIS, but it is not the exact value. A test or tool that
  recomputes a draw elsewhere (for example in Python) disagrees, and a modulo over the rounded value
  is slightly biased.
- **With 7 bytes (56 bits) the value is exact.** It matched Python on three inputs (e.g. `abc` →
  52486384766616015). Suggested change to D3: `draw = first 7 bytes …`. 56 bits is far more range
  than any stream needs.

## V2 — GUID

- `CreateGUID()` is available: 36 characters, uppercase hex with hyphens
  (e.g. `9BF469DC-D274-11F1-BA0F-CE6D9B9D388F`), distinct on consecutive calls. The version nibble is
  `1` (time-based), which is fine for uniqueness across `docker compose down`.
- **Catch in D4**: a GUID is 128 bits, and base32 needs **26** characters for 128 bits; 22 base32
  characters hold only 110. Either use 26 characters or say which 110 bits are kept. The contract
  example `sci_01HZX` does not fix the length.

## V3 — Lock and unique index under concurrency

Two `POST`s sent at the same time from the host to the same key reach two different CSP processes
(pids 1124 and 1122) and overlap, so the gateway does not serialize them.

| Endpoint | First request | Second request |
|---|---|---|
| D5 as designed: `Lock +^…Key(key)`, check, `Hang 2`, insert, unlock | created | waited for the lock, saw the record, created nothing |
| Control: no lock, unique index only | created | had **also** passed the check (`sawExisting: 0`); insert refused with `#5808 Key not unique` |

Both parts of D5's rationale hold: the lock serializes the decide-and-record step, and without it
both racers run the step before the index stops the second one.

## V4 — Holding a response past the client timeout

The CSP Web Gateway has `Server_Response_Timeout=60` (`/usr/irissys/csp/bin/CSP.ini`); Apache's
`Timeout` is 300, so the gateway is the limit. `SN_PARTNER_TIMEOUT_SECONDS` defaults to 60, the
**same** value. Requests sent with `%Net.HttpRequest` from inside the container:

| Case | Server | Client timeout | Client saw |
|---|---|---|---|
| a | `Hang 70` | 120 s | **504** after 60.1 s, the gateway's HTML error page (not JSON) |
| b | `Hang 65` (D6: 60 + 5) | 60 s | timeout (`#5922`) after 60.0 s |
| c | `Set %response.Timeout = sec + 30`, `Hang 70` | 120 s | **200** after 70.0 s, the JSON body |
| d | `Set %response.Timeout = sec + 30`, `Hang 65` | 60 s | timeout (`#5922`) after 60.0 s |

- As designed, D6 is a race. In (b) the client and the gateway both give up at 60 s. The client won
  this run, but a caller with a longer timeout, or a slower client clock, gets the gateway's 504 HTML
  page (a). History would then say `timeout` for what the caller saw as a 5xx, the risk D6 names.
- **Fix, verified**: the holding endpoint sets `%response.Timeout` above the hold before it hangs
  (c, d). The gateway then waits, and the caller always sees its own timeout. No change to
  `CSP.ini`, to `Security.Applications` or to the contract.
- Not run: `EnsLib.HTTP.OutboundAdapter` itself. It sends through `%Net.HttpRequest`, so the same
  behavior is expected; confirm in 008.
