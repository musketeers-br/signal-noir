# Research: Normative Case state machine

**Feature**: [spec.md](spec.md) | **Plan**: [plan.md](plan.md) | **Date**: 2026-10-22

The spec has no `[NEEDS CLARIFICATION]` left, and the five clarify decisions are recorded in it. The questions below are those of the plan's Technical Context: in what form the table is frozen before 10/26, how it is checked, and how the Core inherits it afterwards.

## R1 — Form of the frozen artifact

- **Decision**: besides the Markdown table in the spec, the table is published as data in `contracts/case-state-machine.yaml`: states, transitions T01–T29, attachments per state, refusal rules and the UJ-1 to UJ-4 trace. The YAML is the normative form tools read; the spec is the form people read, and the validator keeps them equal (R2).
- **Rationale**: the acceptance criterion requires a "frozen" table that three fronts read the same way. A prose table cannot be checked by CI against the OpenAPI `CaseState`, `Actor` and `TimelineEventType`. As data, coverage of the 13 states (SC-001) and row completeness (SC-003) become automatic checks, and the Core (Phase B) gains an oracle for the parity test.
- **Alternatives considered**:
  - *Markdown only*: people read it, but nothing stops drift from the OpenAPI or from the Core.
  - *An `x-state-machine` extension inside `openapi-signalnoir.yaml`*: mixes the internal model with the HTTP contract (AD-16 says "internal code-first") and couples this story to the 2.5 freeze.
  - *Writing the Core class now*: forbidden before 10/26 by the Constitution's calendar gate in force at the time (1.1.0; lifted in 1.2.0).

## R2 — How the table is checked before code exists

- **Decision**: a script `contracts/tools/validate_state_machine.py`, in the same style as `validate_fixtures.py` (Python, `uv run --with pyyaml`), run by the `contracts.yml` workflow. It fails when:
  1. the YAML's set of states ≠ the OpenAPI `CaseState` enum;
  2. a non-terminal state has no entry and exit, or a terminal state has an exit;
  3. a transition has no actor, precondition, event or follow-up work; or the actor does not match the `Actor` pattern; or the event is not in `TimelineEventType`; or the command is not in {`Investigate`, `Execute`, `Reconcile`, `Expire`, `Reassess`, `Resume`};
  4. a (from, to) pair appears with two owners from different components that are not distinguishable (duplicate owner, review H-1);
  5. the trace cites a transition that does not exist, or leaves out a step of UJ-1 to UJ-4;
  6. the Id, from, to or actors of some row of the spec's Markdown table ≠ those of the YAML (reading parity).
- **Rationale**: it gives the ticket an executable "verify", reuses the existing tooling and CI (PR #5) and needs no IRIS.
- **Alternatives considered**: a JSON Schema for the YAML alone (does not catch cross-row rules such as coverage and duplicate owners); a Node test next to the prototype (the prototype is throwaway and cannot become a source, per the Constitution).

## R3 — Enum values that do not exist in the contract yet

- **Decision**: the YAML may cite values the spec creates (`outcome_unknown`, the `Annotation` kinds, the `CommandDiscarded` payload, `previousEpisodeCaseId`), marked with `pendingContractChange: "2.5"`. The validator accepts values marked that way and lists them all at the end of the run, so that 2.5 knows what to incorporate. The OpenAPI is **not** edited in this story.
- **Rationale**: freezing the OpenAPI is the scope of 2.5. Editing the contract here without marking the change would break the rule "a divergence becomes an explicit contract-change proposal".
- **Alternatives considered**: editing the OpenAPI now (invades 2.5 and would break the fixtures generated by the prototype); leaving the new values out of the YAML (the validator could not check T26 and D5).

## R4 — How the Core inherits the table from 10/26 on (Phase B, outside this story)

- **Decision**: the Core implements the table as compiled data with no I/O, inside the `SignalNoir.Core` package (AD-1), with a single pure decision function described in [contracts/core-transition-port.md](contracts/core-transition-port.md). A parity test reads `contracts/case-state-machine.yaml` (converted to JSON in the test fixture) and compares it row by row with the compiled table. The test reads a file; the Core does not.
- **Language of the Core: open.** This story does not choose it. The Phase B Plan decides, after the 10/25 spike, between:
  1. ObjectScript, as AD-1 and AD-16 assume today;
  2. Embedded Python methods (`[Language = python]`) inside ObjectScript classes, tested by `%UnitTest` — fits the current Constitution and AD-16;
  3. Embedded Python modules with Python tests — requires amending the Constitution (Engineering Standards: "`%UnitTest` covers the core") and AD-1/AD-16.

  Whatever the choice, the Agent stays on `%AI.Agent`/`%AI.ToolSet`/`%AI.Provider` inside the Production (Constitution, Platform Constraints): the stack research found no Agent or Tool written in Embedded Python.
- **Rationale**: keeps Principle I (the rule lives in the Core, without I/O) and the YAML as the oracle, without generating code from data at runtime (Principle II forbids building executable code from input). Leaving the language open costs nothing now, because this story delivers only data and contract tooling.
- **Alternatives considered**: the Core loading the YAML at runtime (I/O in the Core); generating the Core from the YAML with a script (one more build step, and the diff of generated code is hard to review); fixing ObjectScript or Python now (would commit Phase B before the platform is verified).
- **Platform claims**: no claim about build 154 is used in this story. Checked on 2026-10-22 with iris-agentic-dev on the running dev container: `IRIS 2026.2 (Build 221U)` with Embedded Python 3.12.3, and `%AI.Agent` absent — it is the plain template image, not the contest's AI Hub build 154, so it settles nothing for Q-F. Phase B must verify on build 154 the Embedded Python version and that the parity test can read the JSON fixture from the tests directory in the container.

## R5 — Where to record the replacement of §D and AD-24

- **Decision**: edit `addendum.md` §D (a "Replaced by the normative state machine" note with a link, keeping the old table only as history), the "Pontos fixados" (fixed points) table of AD-24 (same note) and the text of PRD FR-5 (now points to `contracts/case-state-machine.yaml` and to the spec). The decision notebook does not change.
- **Rationale**: spec FR-019. Deleting §D would break the cross-references in the reviews; marking it keeps the history and removes the authority.
- **Alternatives considered**: leaving the documents as they are and only announcing it (the fronts would keep reading §D).

## R6 — Concrete values

- **Decision**: the numbers the table uses are named parameters in the YAML (`approvalTtl: PT15M`, `reassessInterval: PT60S`, `maxInconclusiveReconciliations: 3`, `maxDenials: 2`), not scattered through the row texts.
- **Rationale**: the spec says these values can be adjusted without changing the table. With names, the Core and the Benchmark cite the same parameter.
